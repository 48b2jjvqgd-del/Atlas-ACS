# Service conventions

These conventions are implemented in `@atlas/service-kit` and `@atlas/contracts`. Code that follows the
kit follows the conventions; deviations need a decision record.

## API responses

ATLAS platform APIs (portal and internal) return JSON.

**Success** — `200`/`201` with the standard envelope
([`envelope.ts`](../../packages/contracts/src/http/envelope.ts)):

```json
{
  "data": { "id": "…", "slug": "synthetic-issuer-alpha" },
  "meta": { "correlationId": "…", "apiVersion": "v1" }
}
```

Cross-cutting metadata (pagination, warnings) is added to `meta` as optional fields, so adding it is
backwards-compatible.

**EMV 3DS protocol endpoints are the exception.** They must respond with protocol-defined messages
(ARes, CRes, RRes, Erro) exactly as the specification requires, never with the ATLAS envelope.

## Error responses

Errors use **RFC 9457 Problem Details** with `Content-Type: application/problem+json`
([`problem.ts`](../../packages/contracts/src/http/problem.ts)):

```json
{
  "type": "urn:atlas:problem:validation-failed",
  "title": "Request validation failed",
  "status": 400,
  "instance": "/v1/echo",
  "code": "VALIDATION_FAILED",
  "correlationId": "3f2a1c9e-…",
  "issues": [
    { "path": "body.slug", "message": "Too small: expected string to have >=3 characters" }
  ]
}
```

- `code` is stable and machine-readable; the catalogue is in
  [`packages/shared/src/errors.ts`](../../packages/shared/src/errors.ts). Codes are never repurposed.
- Throw `AtlasError(code, { detail })` for deliberate errors; `detail` must be client-safe.
- Any other error becomes `INTERNAL_ERROR` with a generic message. The original is logged (redacted),
  never returned.
- `instance` excludes the query string.

## Request identity and correlation

| Header             | Meaning                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `x-correlation-id` | Follows one business operation across every hop, HTTP and messaging. Accepted from upstream if it matches `[A-Za-z0-9._:-]{8,128}`, otherwise replaced. Always echoed in the response. |
| `x-request-id`     | One hop. Always generated by the receiving service; client values are ignored.                                                                                                         |
| `x-atlas-caller`   | Calling service name, for diagnostics. **Identification only — not authentication.**                                                                                                   |

Both IDs are attached to every log line for the request.

## Logging

- JSON lines to stdout via Pino; the platform ships logs. Services never write log files.
- Base fields: `service`, `version`, `environment`, `level`, `time` (ISO 8601), `message`; request lines
  add `reqId`, `correlationId`.
- Successful API requests log one `request completed` line at `info` (route template, status,
  duration); infrastructure endpoints log at `debug`. 4xx log at `info`, 5xx at `error` with the error.
- **Never log** passwords, OTPs, secrets, tokens, private keys, PANs, CVV/CVC, track data, expiry dates,
  authentication values (CAVV/AAV) or ephemeral keys. Every log object passes through key-based
  redaction and every message through Luhn-based PAN scrubbing — a safety net, not a licence.
- Never log request or event _payloads_ wholesale; log identifiers.

## Configuration

- Environment variables only, validated with Zod at startup
  ([`config.ts`](../../packages/service-kit/src/config.ts)). Invalid configuration stops the process with
  exit code 1 and a single JSON line naming the invalid keys — **values are never printed**.
- Empty strings are treated as unset. Booleans accept only `true/false/1/0`.
- Secrets may be supplied as `NAME_FILE` (path to a file) instead of `NAME`; supplying both is an error.
- Connection URLs (`DATABASE_URL`, `VALKEY_URL`, `RABBITMQ_URL`) are required exactly when a service
  declares that dependency.
- `HOST` defaults to `127.0.0.1` (containers set `0.0.0.0`). `PORT` defaults to the catalogue port.

Common keys: `ATLAS_ENV`, `HOST`, `PORT`, `LOG_LEVEL`, `LOG_PRETTY`, `SHUTDOWN_TIMEOUT_MS`,
`READINESS_CHECK_TIMEOUT_MS`, `ATLAS_BUILD_SHA`, `OTEL_EXPORTER_OTLP_ENDPOINT`.

## Validation

- All external input is validated with Zod schemas from `@atlas/schemas` / `@atlas/contracts`. Routes
  declare them in Fastify's `schema` option (`params`, `querystring`, `body`, `headers`).
- Validate at boundaries: HTTP input, message consumption, configuration, and responses from other
  services (`createServiceClient` validates against the callee's contract).
- Primitives (UUIDs, correlation IDs, slugs, timestamps) are defined once; never redefine them inline.
- Default body limit is 256 KiB.

## Service contracts and versioning

- HTTP APIs are versioned in the path: `/v1/...`. Infrastructure endpoints (`/health/*`, `/info`,
  `/metrics`) are unversioned paths with versioned payload schemas.
- Event types carry their major version: `atlas.<domain>.<name>.v<major>`.
- **Backwards-compatible (same version):** adding optional request fields, adding response fields,
  adding new endpoints, adding new error codes.
- **Breaking (new major):** removing or renaming fields, changing types or meaning, making optional
  fields required, tightening validation. Run old and new versions side by side until consumers move.
- Consumers must ignore unknown fields.
- Every contract is exported as JSON Schema (`pnpm --filter @atlas/contracts export:json-schema`) and
  published as a CI artefact.

## Communication

### Synchronous (HTTP)

- Use `createServiceClient` ([`http-client.ts`](../../packages/service-kit/src/http-client.ts)).
- Every call has an explicit timeout. Timeouts map to `UPSTREAM_TIMEOUT`, connection failures to
  `DEPENDENCY_UNAVAILABLE`.
- No automatic retries. Retries multiply latency and load on the authentication path; callers retry
  explicitly and only for idempotent operations, within the remaining time budget.
- Correlation ID and caller name are always propagated.
- Responses are validated against the callee's published contract.

### Asynchronous (RabbitMQ)

Implemented in [`messaging.ts`](../../packages/service-kit/src/messaging.ts).

| Element      | Convention                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Envelope     | CloudEvents 1.0 structured JSON (`application/cloudevents+json`) with `correlationid` and optional `tenantid` extensions         |
| Exchange     | `atlas.events`, durable topic exchange; routing key = event type                                                                 |
| Queues       | `<consumer-service>.<purpose>`, durable **quorum** queues, each owned by one consumer                                            |
| Dead letters | `atlas.events.dlx` → `<queue>.dlq`                                                                                               |
| Publishing   | Confirm channels, persistent messages; payload validated before send; only the contract's registered producer may publish        |
| Consuming    | Envelope and payload validated; invalid or failing messages are dead-lettered — never dropped silently, never requeued in a loop |
| Delivery     | At-least-once. Consumers must be idempotent, keyed on the event `id`                                                             |

Retry with back-off, consumer resubscription after reconnect, and the transactional outbox pattern (to
publish atomically with a database write) are planned for Stage 1A.

## Health and lifecycle

- `/health/live` — process is running; never checks dependencies (a dependency outage must not cause
  restarts).
- `/health/ready` — all registered checks pass within `READINESS_CHECK_TIMEOUT_MS`; `503` otherwise and
  during shutdown. Failure reasons are reduced to safe codes (`ECONNREFUSED`, `timeout`).
- Shutdown on `SIGTERM`/`SIGINT`: mark not-ready → stop accepting connections → drain in-flight requests
  → close connections → exit 0. Exceeding `SHUTDOWN_TIMEOUT_MS` forces exit 1.
- Startup never blocks on infrastructure: connections are lazy and readiness reports their state.

## Testing conventions

| Suite                 | Location                               | Needs                        | Runs                     |
| --------------------- | -------------------------------------- | ---------------------------- | ------------------------ |
| Unit                  | `**/src/**/*.test.ts` next to the code | nothing                      | every PR                 |
| Smoke                 | `tests/smoke`                          | a build                      | every PR                 |
| Integration           | `tests/integration`                    | PostgreSQL, Valkey, RabbitMQ | every PR (Compose in CI) |
| E2E                   | `tests/e2e` (Playwright)               | a portal build               | every PR                 |
| Protocol / Compliance | `tests/protocol`, `tests/compliance`   | —                            | from Stage 1B / 4        |

Tests assert behaviour, not implementation: prefer real sockets, real processes and real infrastructure
over mocks; stub only at network boundaries. Test data is synthetic; test PANs are well-known public test
numbers or generated Luhn-valid numbers.
